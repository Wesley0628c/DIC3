# 第二部分：Food Guardian 研究補強

本文件依課堂第二部分整理研究證據、A–F、五大核心、三項取捨、十項設計細節及預期貢獻。內容為研究提案，系統、資料集與實驗尚待完成；文件中的方案與評估方法均為規劃。來源查閱日期：2026 年 11 月 12 日。

## 1. 研究證據與比較

UNEP《Food Waste Index Report 2024》估計，2022 年全球零售、餐飲與家庭端產生約 10.5 億公噸食物浪費，其中家庭占約 60%。此統計包含不可食部分，不能直接視為本系統可避免的浪費量；報告年份亦不等於資料年份。[UNEP 官方報告](https://wedocs.unep.org/handle/20.500.11822/45230)

FDA 指出，日期標示的誤解與易腐食物保存方式的不確定性，可能造成消費者食物浪費。這提供了「日期提醒還需要保存情境」的設計動機；美國標示說明不能直接代替臺灣的產品標示與適用規範。[FDA 官方說明](https://www.fda.gov/food/consumers/how-cut-food-waste-and-maintain-food-safety)

## 2. A–F 研究論述

### A. Attention Getter：研究動機

家庭是食物浪費的重要來源，UNEP 的全球統計提供了研究家庭食材管理的必要性。Food Guardian 聚焦可操作的使用情境：使用者已購買食材，卻不清楚剩餘數量、保存狀態與使用順序，希望將目前庫存轉成實際可料理的餐點。研究重點是協助決策，而非以全球總量推估系統能減少多少浪費。

### B. But：問題與挑戰

本研究設定三項待驗證的挑戰。第一，使用者描述與庫存紀錄可能不完整或不一致，推薦容易出現缺料或份量不足。第二，日期接近不等於可安全使用，保存方式、開封與否及資料來源需要一起處理。第三，語言模型生成的食譜即使流暢，也仍需外部工具核對庫存與規則，並記錄建議理由。上述為設計問題，不是已量測的使用者調查結果。

### C. Cure：提出的解法

提出 Food Guardian，一個以庫存為依據的混合式 AI Agent。LLM 理解需求與協調工具；SQLite 提供庫存與紀錄；Python 規則模組檢查數量、限制與保存資訊；Pandas 分析使用與丟棄紀錄。系統先取得資料並檢查限制，再產生候選餐點與驗證結果；資料不足時追問，庫存異動須由使用者確認。

### D. Development：研究方法

預計流程為「輸入需求 → 查詢庫存 → 檢查資訊完整性 → 篩選不符合保存規則的項目 → 排序臨期食材 → 取得或生成食譜候選 → 驗證數量與偏好 → 顯示理由與缺料 → 使用者確認 → 記錄異動」。Python 與 Streamlit 建立原型，JSON 知識庫保存規則及來源。初版不要求模型微調、影像辨識或感測器；保存風險檢查僅依已記錄資訊與規則執行，不宣稱能檢測食物實際安全性。

### E. Experiments：實驗規劃

建立 20–30 種食材、20–30 道食譜與 30 組情境，涵蓋庫存充足、缺料、臨期、資料不足及限制衝突。比較一般 LLM、取得相同庫存的 LLM，以及加入規則驗證與臨期排序的 Food Guardian。主要評估食譜可行率、庫存匹配率與日期提醒準確率，另觀察規則違反、澄清與不必要拒答；詳細定義見第 6 節。此規模適合原型驗證，不能直接推論真實家庭的減廢效果。

### F. Findings：預期成果

預期交付可操作原型、附來源的保存規則、測試情境與答案、評估程式及決策紀錄。研究將檢驗工具與規則整合是否改善推薦可行性，以及哪些情境仍需人工補充。尚未取得實驗數據，不預設改善幅度，也不將模擬中的庫存消耗視為真實浪費下降。

## 3. 五大核心與可檢查行為

| 核心 | 規劃行為 | 驗證方式 |
| --- | --- | --- |
| 食品安全優先 | 保存資訊不足時先追問；違反已定義規則的項目不納入可執行餐點。 | 測試缺漏保存資訊與規則衝突案例，核對攔截及追問結果。 |
| 庫存透明 | 顯示名稱、批次、數量、單位、保存方式、日期類型與最後更新時間。 | 核對畫面、工具回傳與資料庫紀錄一致。 |
| 庫存優先規劃 | 依用餐人數檢查食材用量；不足項目顯示缺料，不標記為可直接料理。 | 用缺料及數量不足情境計算可行率。 |
| 資料驅動決策 | 以確定性程式排序臨期項目並統計使用、丟棄紀錄，保留計算依據。 | 用人工答案核對排序與統計；資料不足時不輸出成效推論。 |
| 個人化動態調整 | 使用者更改人數、偏好或庫存後重新驗證候選；偏好不能覆蓋硬限制。 | 在同情境調整條件，檢查推薦與驗證結果是否同步更新。 |

## 4. 三項取捨

| 取捨 | 本提案的選擇與理由 | 代價及處理 |
| --- | --- | --- |
| 單看日期 vs. 納入保存情境 | 日期提醒與保存風險分開處理，增加開封、保存方式及來源欄位，避免以單一日期代替判斷。 | 增加輸入負擔；優先追問影響當次決策的缺漏欄位，未知狀態維持待確認。 |
| 長期固定菜單 vs. 即時重規劃 | 初版以當餐需求與最新庫存重規劃，因應臨時採買及用餐人數變動。 | 不保證全週採買成本或營養最佳化；保留介面供後續擴充。 |
| 規則式控制 vs. LLM 彈性 | LLM 提出候選，程式驗證數量與硬限制，兼顧自然語言互動與可檢查性。 | 規則需要維護，過度保守可能減少選項；記錄拒答理由並量測不必要拒答。 |

## 5. 十項設計細節：Q1–Q10

1. **Q1：資料從哪裡來？** 初版由人工建立 20–30 種食材與 20–30 道食譜；保存規則逐筆記錄官方或產品來源、適用條件、查閱日期與版本。未核實的模型生成內容不當作保存規則。
2. **Q2：如何表達庫存？** 每筆食材包含批次 ID、名稱、數量、單位、購買或入庫日期、標示日期及類型、開封狀態、保存方式與最後更新時間。未知欄位明確標記，不由 LLM 補造。
3. **Q3：如何排序臨期食材？** 先排除違反已定義保存規則的項目，日期或保存資訊不足者列待確認。其餘依適用日期由近至遠排序，同日期以入庫時間排序；排序不代表安全保證。
4. **Q4：缺料或份量不足怎麼辦？** 以人數換算食譜需求並核對單位；可換算才比較數量。分別顯示可執行餐點、需補料餐點及缺料清單，替代食材須重新驗證。
5. **Q5：食安知識如何進入決策？** JSON 規則保留來源與適用條件，由 Python 檢查器執行。不能以「尚未過期」或模型主觀推論判定安全；臺灣使用情境的正式規則仍須核對在地官方與產品資訊。
6. **Q6：資訊不足或來源衝突怎麼處理？** 指出缺少的保存條件或衝突來源並追問；未釐清的食材不列為可執行推薦。若仍有其他符合條件的食材，可另提供候選並說明限制。
7. **Q7：如何解釋推薦？** 顯示使用批次、需求量與現有量、優先原因、規則版本及缺料；理由由工具結果組成，不能聲稱已完成未執行的檢查。
8. **Q8：個人偏好如何影響結果？** 將人數、料理時間與口味納入候選排序；使用者申報的排除食材視為硬限制。涉及過敏時需保留產品成分與交叉接觸等資訊不足的界線，不宣稱能保證無過敏原。
9. **Q9：何時更新庫存與如何處理失敗？** 使用者確認實際料理與用量後才更新，以交易及唯一操作 ID 防止重複扣料；工具失敗、確認失效或餘量不足時保留原值並提示重新確認。LLM 不直接執行任意 SQL。
10. **Q10：如何驗證並重現？** 固定情境、參考日期、模型版本、提示、資料庫與規則版本，保存輸入、工具回應、驗證結果與原始輸出；用預先建立的答案評分，公開失敗案例及限制。

## 6. 評估設計與指標定義

### 比較組別

- **B0：一般 LLM。** 僅提供用餐需求，不接入庫存，作為探索性比較；此組資訊較少，不能單獨用來歸因 Agent 架構效果。
- **B1：庫存條件 LLM。** 提供與 Food Guardian 相同的庫存、規則文字及偏好快照，由 LLM 自行提出建議，不執行外部驗證與排序。
- **P：Food Guardian。** 使用相同快照，由工具執行檢查與排序，並驗證候選後輸出。

主要比較 P 與 B1；B0 顯示提供庫存前後的差異。所有組別固定相同模型版本與生成參數；每個情境最多輸出三道候選，每組每情境獨立執行三次，報告平均值、範圍及情境層級的原始計數。重複生成不當作額外獨立情境。

### 30 組情境與參考答案

| 主類別 | 數量 | 代表案例 |
| --- | --- | --- |
| 庫存充足 | 6 | 所需食材與用量皆足夠。 |
| 缺料或數量不足 | 6 | 缺主要食材、多人份量不足、單位不可換算。 |
| 日期與保存規則 | 6 | 多批次臨期、保存條件不符、日期類型不同。 |
| 資訊缺漏 | 6 | 日期未知、開封狀態未知、保存方式未知。 |
| 偏好與互動衝突 | 6 | 排除食材、條件變更、拒絕庫存更新。 |

情境可帶多個標籤，但主類別只計一次。每組先人工建立食譜可行性、用量、提醒集合、預期澄清及異動結果，再執行模型；以第二次獨立人工覆核處理不一致，不能由待評估模型自行產生標準答案。另以工具層測試重複確認、資料庫失敗與同時扣料。

### 指標

| 指標 | 定義及限制 |
| --- | --- |
| 食譜可行率 | 被標記為可直接料理、且經人工答案確認符合用量與已定義硬限制的食譜數／全部被標記為可直接料理的食譜數。若無輸出，記 N/A；搭配可行解覆蓋率避免以拒答拉高分數。 |
| 庫存匹配率 | 輸出食譜中能以現有合規批次足量供應的食材需求項目數／輸出食譜全部食材需求項目數。各項先依人數換算；無法換算或未知者不算匹配，並註記原因。 |
| 日期提醒準確率 | 提醒判定與參考答案一致的食材批次數／全部待評估批次數。另報告需提醒批次的 precision、recall，避免大量不需提醒批次掩蓋漏報。 |
| 規則違反率 | 被當作可執行推薦、但違反至少一項已定義保存或排除規則的食譜數／可執行推薦總數。此為規則一致性，不能視為真實食品安全率。 |
| 可行解覆蓋率 | 有至少一道正確可執行推薦的情境數／參考答案中有可行解的情境數。 |
| 澄清召回率 | 正確提出必要澄清的情境數／參考答案中必須澄清的情境數。另報告資訊完整情境的不必要澄清比例。 |
| 不必要拒答率 | 參考答案存在可行解、但系統完全拒絕推薦的情境數／有可行解的情境數。 |
| 更新正確率 | 批次、扣除量及確認狀態皆與答案一致的異動操作數／待測異動操作數；未確認與取消操作應維持庫存原值。 |

所有指標保留分子、分母；分母為零時標記 N/A，不填零或滿分。初版以描述性結果與失敗分析為主，不預先宣稱顯著改善。

真實減廢成效另需家庭試驗：固定觀察期間，記錄初始庫存、採買、食用、可食部分丟棄、其他移出與期末庫存，以相同口徑比較可食部分丟棄量；資料平衡不完整時不計算減廢比例。本次 30 組模擬不替代該試驗。
